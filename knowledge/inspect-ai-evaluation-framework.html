Inspect (UK AI Security Institute Evaluation Framework)

frameworkfreshness: volatilekey claims checked 2026-10-09

Inspect is an open-source Python framework from the UK AI Security Institute for running LLM evaluations: you define a task from a dataset, a solver and a scorer, and Inspect runs it against any supported model and logs everything for review.

Short answer: Inspect (inspect_ai) is an MIT-licensed framework created by the UK AI Security Institute for LLM evaluations. A Task = dataset + solver + scorer; it supports tool use, agents, sandboxed code execution, model-graded scoring, a log viewer and a library of 200+ pre-built evaluations (Inspect Evals).

What is it?

Think of Inspect as a test harness for AI models. You write down questions (the dataset), how the model should attempt them (the solver — a plain prompt, a tool-using agent, a multi-step plan), and how to mark the answers (the scorer — exact match, a model acting as a grader, or custom code). Inspect runs it against whichever model you point it at, keeps detailed logs, and gives you a viewer to see exactly what happened.

Also known as: Inspect AI, inspect_ai, UK AISI Inspect, AI Security Institute Inspect, Inspect evals, inspect_evals, Inspect framework, UK AI Safety Institute evaluation framework.

Technical definition

Inspect's README describes it as a framework for large language model evaluations created by the UK AI Security Institute, with built-in components for prompt engineering, tool usage, multi-turn dialogue and model-graded evaluations, extensible through other Python packages, and a collection of over 200 pre-built evaluations. Its documentation organises the framework into: Tasks (datasets, solvers and scorers brought together), Datasets, Solvers (prompt engineering and other elicitation strategies), Scorers (including text-matching, multiple-choice, model-graded and math scorers, with metrics and epoch reduction); Models (a uniform API across providers, plus caching, concurrency control, batch mode, reasoning-model options and structured output); Agents (ReAct agent, a "deep agent", multi-agent composition, custom agents, an agent bridge for frameworks such as OpenAI Agents SDK, LangChain and Pydantic AI, and a human agent for baselining); Tools (custom tools, standard tools for code execution, text editing, computer use, web search and browsing, and MCP tools); Sandboxing to isolate model-generated code; tool approval and result-review policies; limits on time, messages, tokens and cost; eval sets for running many tasks; log files, dataframes and a log viewer ("Inspect View") with a VS Code extension; and scanners that review transcripts for problems such as misconfigured environments or refusals. The pre-built evaluations live in the separate Inspect Evals repository, which is maintained by Generality Labs with contributions from the UK AI Security Institute and others, not by the Institute alone. The source repository licence is MIT.

Entity type: framework · Freshness class: volatile.

When should I use it?

Use when you need repeatable, inspectable LLM or agent evaluations, particularly with tools and sandboxes. For a quick check of one prompt, a handful of manual test cases may be enough.

Implementation patterns

  • Define a Task from a dataset, a solver and a scorer; run it with the inspect CLI against a model identifier.
  • Use model-graded scorers for open-ended answers, and spot-check them against human labels.
  • Run agent evaluations inside a sandbox with limits on tokens, messages and time.
  • Re-score saved logs without re-running the model.
  • Run eval sets across several models and compare with the analysis tools.

Technologies and frameworks

Commonly associated: inspect_ai (Python), Inspect Evals, Inspect View, VS Code extension, Docker-based sandboxes, model providers via a uniform API. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Write 20–50 representative samples with clear targets.
  2. Choose the simplest solver that reflects real use (plain generation first, tools later).
  3. Pick a scorer you can audit; add a model-graded scorer only when exact checks are impossible.
  4. Run against a small model first to debug, then your target models.
  5. Open the log viewer and read failures before reading the aggregate score.
  6. Record versions and settings so others can reproduce the run.

Common failure modes

  • Treating a pre-built eval score as proof of real-world safety or capability (Public Benchmarks vs Task-Specific Evals).
  • Letting an agent run unsandboxed code with real credentials.
  • Trusting a model-graded score without calibration against humans (LLM-as-a-Judge).
  • Comparing scores across runs with different prompts, epochs or limits.
  • Evaluating on data the model may have seen (Benchmark Contamination and Data Leakage).

Troubleshooting

  • Scores differ between runs — Fix seeds where supported, set the number of epochs, and report uncertainty rather than a single number.
  • Agent evaluation hangs or costs too much — Set message, token, time and cost limits on the task.
  • Cannot reproduce a published result — Check the eval version, prompt, model snapshot and scorer settings recorded in the log.

Contrasted with

  • MLflow — MLflow tracks experiments and models across the ML lifecycle; Inspect specialises in LLM evaluation harness features (solvers, scorers, sandboxes).
  • LLM-as-a-Judge — Model grading is one scorer type inside Inspect, not a replacement for the framework.
  • HumanEval and Code Generation Benchmarks — HumanEval is a benchmark; Inspect is the harness that can run benchmarks like it.
