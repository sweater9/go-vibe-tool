Chain-of-Thought Prompting

techniquefreshness: evolvingsources not yet verified

Chain-of-thought prompting asks a model to lay out intermediate steps before answering, which can improve multi-step reasoning on some tasks.

Short answer: Chain-of-thought (CoT) means getting the model to write intermediate steps before the answer. It can help multi-step problems, but the written steps are not a guaranteed faithful explanation and many reasoning models already do it internally.

What is it?

Chain-of-thought prompting means asking a model to show its working: "work through this step by step, then give the final answer". For multi-step problems that often gives better answers than demanding the answer straight away.

Two cautions: the steps written out are output text, not a guaranteed window into how the model actually decided; and newer reasoning models often do this by themselves.

Also known as: CoT, CoT prompting, step by step prompting, think step by step, let's think step by step, show your work prompt, few-shot chain of thought, zero-shot CoT.

Technical definition

CoT elicits intermediate token sequences via few-shot exemplars or instructions (zero-shot "let's think step by step" variants). It improves performance on arithmetic, symbolic and commonsense multi-step tasks for sufficiently capable models (Wei et al., 2022). Stated rationales can be unfaithful to the computation that produced the answer, so they should not be treated as ground-truth explanations. With reasoning-trained models, explicit CoT prompts are often unnecessary and can interfere (Reasoning Models).

Entity type: technique · Freshness class: evolving.

When should I use it?

Try CoT for multi-step arithmetic, logic, planning and analysis with standard (non-reasoning) models. Skip it for extraction/classification, or when using a reasoning model whose provider advises against explicit step-by-step prompts.

Implementation patterns

  • Few-shot CoT: include 2–4 worked examples with steps and a final answer line.
  • Zero-shot CoT: instruct stepwise working, then a clearly delimited final answer.
  • Decompose: ask for sub-questions first, answer each, then combine.
  • Separate fields: ask for a brief "justification" and a "final_answer" in a structured output so downstream code reads only the answer.

Technologies and frameworks

Commonly associated: few-shot exemplars, structured output with a "rationale" field. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Write the task, the constraints and what a correct final answer looks like.
  2. Add "work through the problem, then end with FINAL: <answer>" or use a structured schema.
  3. Test with and without CoT on the same cases (How to Evaluate AI Systems and Outputs).
  4. Keep it only where it measurably helps.
  5. If showing users reasoning, present a concise rationale you generated for display.

Common failure modes

  • Parsing the final answer out of free-form steps, which breaks when the format drifts.
  • Trusting a plausible-looking chain as proof; errors can hide in a fluent step.
  • Adding CoT to a reasoning model and getting longer, no better, more expensive output.
  • Exposing raw intermediate text to end users when a short justification would do (Reasoning Transparency and Hidden Reasoning).
  • Using CoT for simple lookups where it only adds tokens.

Troubleshooting

  • Final answer is hard to extract — Require a labelled final line or structured output (Structured Outputs from LLMs).
  • Steps are plausible but answer is wrong — Add a verifier (calculator, unit tests, retrieval) rather than asking the model to re-check itself.
  • Quality dropped with a reasoning model — Remove step-by-step scaffolding and state the goal and constraints instead.

Contrasted with

  • Reasoning Models — Reasoning models deliberate by default after special training; CoT is a prompting technique you add.
  • Self-Consistency (Sampling and Voting) — Self-consistency samples several chains and votes; plain CoT uses one chain.
