MCP Security Risks and Mitigations

techniquefreshness: volatilesources not yet verified

MCP servers can read data and take actions for an AI application, so they carry risks: malicious or compromised servers, tool-description poisoning, over-broad permissions and prompt injection through tool results.

Short answer: Treat every MCP server as code with access to your data. Review before installing, grant least privilege, require human approval for sensitive tools, isolate credentials, and treat tool descriptions and results as untrusted input.

What is it?

An MCP server is a plug-in that can touch your files, accounts and APIs. A bad or hijacked one — or good one that returns booby-trapped text — can trick an assistant into leaking data or doing something harmful. The defence is the same as for any software supply chain, plus care about what the model is allowed to do on its own.

Also known as: MCP risks, tool poisoning, MCP prompt injection, secure MCP servers, MCP authorization, MCP best practices security, malicious MCP server, MCP supply chain.

Technical definition

Risk classes widely discussed for MCP and similar tool ecosystems: untrusted or malicious servers (supply-chain); tool-description injection ("tool poisoning") where metadata contains hidden instructions; indirect prompt injection via tool results (What is Prompt Injection?); excessive permissions and token scope; confused-deputy problems when a server uses its own credentials on a user's behalf; credential exposure in configs; rug-pull updates that change behaviour after approval; and cross-server data leakage when several servers share one context. The MCP specification and its security guidance, plus OWASP LLM guidance, describe mitigations; details evolve.

When should I use it?

Apply to every MCP deployment, especially with third-party servers.

Implementation patterns

  • Vendor review and pinning of server versions/hashes.
  • Per-server least-privilege credentials, short-lived tokens.
  • Human confirmation for writes, deletes, payments and external sends.
  • Run local servers in a sandbox with restricted file/network access.
  • Log tool calls and review anomalies.

Technologies and frameworks

Commonly associated: MCP specification security guidance, OAuth 2.x, sandboxing (containers, microVMs), secret managers, allow-lists. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Inventory connected servers and their permissions.
  2. Remove unused ones.
  3. Scope credentials narrowly.
  4. Sandbox local servers.
  5. Require approvals for sensitive tools.
  6. Monitor and rotate secrets.

Common failure modes

  • Auto-approving all tool calls.
  • One server with a broad personal access token.
  • Secrets in shared config files.
  • Trusting tool descriptions as safe.
  • Ignoring updates that change tool behaviour.

Troubleshooting

  • Unexpected outbound requests — Block egress by default; allow-list destinations; inspect server code.
  • Model follows odd instructions after a tool call — Treat the result as untrusted; strip/flag instructions; require confirmation for actions.

Contrasted with
