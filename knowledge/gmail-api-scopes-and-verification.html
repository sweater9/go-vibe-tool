Gmail API Scopes and Verification

standardfreshness: volatilekey claims checked 2026-10-09

Gmail API scopes fall into non-sensitive, sensitive and restricted classes. Restricted scopes (including gmail.readonly) require OAuth app verification, a security assessment if you store the data on servers, and Google's Limited Use rules, which bar using that data to train generalised AI models.

Short answer: Before an AI agent reads mail, choose the narrowest Gmail scope: gmail.labels is non-sensitive, gmail.send is sensitive, and gmail.readonly, gmail.modify, gmail.compose, gmail.metadata and mail.google.com are all restricted — they need app verification and, when you store the data on your servers, a security assessment. Google's policy also forbids using this data to train or improve AI/ML models beyond that user's own personalised feature.

What is it?

"Readonly" sounds harmless, but for Gmail Google treats reading mail as one of its most sensitive permissions. If your app is for other people, you must pass Google's verification review, and if you keep their email data on a server you may need an independent security assessment. Google's rules also limit what you can do with the data: you can show it to the user inside your feature, but you cannot use it to train a general AI model or sell it. That matters a lot when the product is an AI agent.

Also known as: Gmail restricted scopes, gmail.readonly restricted, Gmail OAuth scopes, Google OAuth app verification, Google security assessment CASA, Limited Use policy Gmail, Google user data policy AI training, Gmail API permissions for agents.

Technical definition

Google's Gmail API scope page (checked on the date below) classifies scopes as: https://www.googleapis.com/auth/gmail.labels — non-sensitive; gmail.send — sensitive; and restricted: https://mail.google.com/, gmail.readonly, gmail.compose, gmail.insert, gmail.modify, gmail.metadata, gmail.settings.basic and gmail.settings.sharing (the last is described as restricted to administrative use by Google Workspace customers with a service account and domain-wide delegation). The page says restricted scopes "provide wide access to Google user data and require restricted scope OAuth App Verification" and that if you store restricted-scope data on servers (or transmit it) you must go through a security assessment. Google's Workspace user-data and developer policy (last updated 2026-09-03 on the date checked) sets Limited Use rules: limit use to providing or improving visible user-facing features; restrict transfers to consented feature delivery, security, legal compliance or an acquisition with consent; do not let humans read user data except with documented consent, for security, for legal compliance, or in aggregated and anonymised form; and prohibits transferring, selling or using user data to serve ads, to determine creditworthiness, or "to create, train, or improve a machine learning or artificial intelligence model beyond that specific user's personalized model for the appropriate use case or user-facing feature". Apps must include an attestation sentence about adhering to the Google User Data Policy including Limited Use. The older Google API Services User Data Policy page (last updated 2024-02-15) contains the human-reading and transfer limits but the AI/ML sentence was not found on it at check time, so treat the Workspace policy page as the source for that rule.

When should I use it?

Read before choosing scopes for any Gmail-connected agent or when drafting a privacy notice for one. Not legal advice; confirm with Google's current policy and your counsel.

Implementation patterns

  • Map each tool to one scope: labelling → gmail.labels; sending → gmail.send; reading → a restricted scope (plan for verification).
  • Keep restricted-scope data off your servers where you can (client-side or per-request processing) to reduce assessment burden — confirm with Google's current requirements.
  • Never feed mailbox content into training or fine-tuning sets.
  • Document data flows and retention in the privacy policy and in the verification submission.

Technologies and frameworks

Commonly associated: Gmail API, Google OAuth 2.0, restricted-scope verification, Limited Use policy. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. List the exact actions the agent needs.
  2. Select the narrowest scope per action and check its class on the scopes page.
  3. Decide whether you will store mail data server-side; if so plan for the security assessment.
  4. Add the Limited Use attestation and a plain-language data-use notice.
  5. Exclude mail content from training, tuning and shared evaluation sets.
  6. Re-check Google's pages before launch — classes and policies change.

Common failure modes

  • Assuming "readonly" is a low-friction scope.
  • Shipping a prototype on a restricted scope to external users without verification.
  • Logging message bodies into an observability or evaluation dataset that is later used to tune a model.
  • Letting engineers browse user mail for debugging without the documented consent the policy requires.
  • Using the full-access scope mail.google.com when a narrower one exists.

Troubleshooting

  • Verification is rejected — Reduce requested scopes to what visible features need and explain each in the submission.
  • Need to debug with real messages — Use synthetic or consented test accounts; do not read user mail without documented consent.
  • Want to improve summaries using users' mail — Do not train a generalised model on it; per-user personalisation inside the feature is the allowed carve-out under the policy wording.
