Outcome Reward Model (ORM)

modelfreshness: evolvingsources not yet verified

An outcome reward model scores a completed answer, judging only whether the final result is right (or preferred), not the steps that led to it.

Short answer: An ORM judges the final answer only. It is cheaper to train than a PRM (you only need final-answer correctness) but gives sparse feedback and can reward lucky or flawed reasoning that reached the right answer.

What is it?

An outcome reward model is a grader for finished answers. It looks at the end result — "was the final answer right?" — and gives a score. It ignores whether the working was sound.

That is cheap and simple to get labels for (you only need to know the right answer), but it can reward a lucky guess or flawed reasoning that happened to land on the correct answer.

Also known as: ORM, outcome supervision, outcome-based reward, answer verifier, final-answer verifier, outcome-based feedback.

Technical definition

An ORM is trained to predict final-answer correctness (or preference) from a complete solution; Cobbe et al. (2021) trained such verifiers to rerank GSM8K samples. In RL it supplies a sparse terminal reward. Compared with process supervision it needs only outcome labels, but credit assignment across steps is weak and reasoning that reaches correct answers by faulty means is rewarded (Uesato et al., 2022 compare outcome- and process-based feedback). In domains with exact checkers, a programmatic verifier replaces the learned ORM (Reinforcement Learning for Reasoning (RLVR and GRPO)).

Entity type: model · Freshness class: evolving.

When should I use it?

Use when the final result is checkable and the path matters less, or labelling effort must stay low.

Prerequisites and related concepts

Understand these first: Reinforcement Learning, Best-of-N Sampling.

Related concepts: Process Reward Model (PRM), PRM vs ORM: Process vs Outcome Reward Models, Reinforcement Learning for Reasoning (RLVR and GRPO), Reward Hacking and Over-Optimization, RLHF (Reinforcement Learning from Human Feedback).

Implementation patterns

  • Exact check: compare to a known answer or run unit tests, no learning required.
  • Learned ORM reranking of N samples.
  • Terminal reward in RL for verifiable tasks.
  • Mixed: ORM for ranking, PRM for diagnosing errors.

Technologies and frameworks

Commonly associated: programmatic verifiers (unit tests, exact match), learned verifiers, GSM8K / MATH answer checkers. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Pick a programmatic checker when possible.
  2. Otherwise label final-answer correctness for a diverse set of solutions.
  3. Train and validate the ORM, checking calibration.
  4. Use it for reranking before using it in RL.
  5. Audit selected samples for flawed reasoning.

Common failure modes

  • Rewards correct answers reached through invalid reasoning.
  • Sparse signal makes RL slow or unstable on long chains.
  • Learned ORM exploited by plausible-but-wrong answers.
  • Answer-format mismatches scored as wrong.

Troubleshooting

  • Right answers with bad reasoning are rewarded — Add step checks, or a PRM, or audit samples by hand.
  • Format mismatches scored wrong — Normalise answers (units, formatting) in the checker.
  • RL learns slowly — Use curriculum, easier problems first, or denser rewards.

Contrasted with

  • Process Reward Model (PRM) — PRM scores steps; ORM scores only the end result.
