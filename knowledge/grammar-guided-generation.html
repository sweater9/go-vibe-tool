Grammar-Guided Generation (CFG and Regex Constraints)

techniquefreshness: evolvingsources not yet verified

Grammar-guided generation constrains a model with a formal grammar or regular expression so output belongs to a defined language — a config format, a small SQL subset, an ID pattern.

Short answer: Express the allowed output as a grammar or regex and have the decoder only permit tokens that can still lead to a valid string. Useful for small formal languages; keep grammars simple and test them against token boundaries.

What is it?

Sometimes the output is not JSON but some other strict format: a date pattern, a tiny query language, a command. A grammar describes exactly which strings are legal, and the decoder uses it to rule out illegal continuations as the model writes.

Also known as: CFG decoding, context free grammar LLM, regex constrained generation, grammar sampling, formal grammar decoding, grammar based sampling.

Technical definition

Regular expressions map to finite-state machines; context-free grammars require pushdown-style parsing (e.g., Earley/LR-style or specialised engines). The decoder intersects the grammar state with the tokenizer vocabulary to compute allowed tokens per step. Pitfalls: ambiguity between grammar terminals and sub-word tokens, left recursion, and large vocabularies slowing mask construction. See GBNF Grammars (llama.cpp) for llama.cpp's grammar format and Constrained Decoding (Guided Generation) for the general technique.

Entity type: technique · Freshness class: evolving.

When should I use it?

Use for small, strict formal outputs, especially with local engines; for ordinary JSON, a schema is simpler.

Prerequisites and related concepts

Understand these first: Constrained Decoding (Guided Generation).

Related concepts: GBNF Grammars (llama.cpp), Outlines (Structured Generation Library), Structured Outputs from LLMs, JSON Schema.

Implementation patterns

  • Regex for identifiers, dates and enums.
  • Small CFG for DSLs and command languages.
  • Grammar + post-validation (execute in a sandbox or parse with a real parser).
  • Keep grammar minimal and extend only when tests fail.

Technologies and frameworks

Commonly associated: llama.cpp GBNF, Outlines, XGrammar, Lark-style grammar tools. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Define the language with examples of valid/invalid strings.
  2. Write the minimal grammar.
  3. Test the grammar with a parser, independent of the model.
  4. Decode under the grammar.
  5. Validate semantics and run in a sandbox.

Common failure modes

  • Grammar valid but semantically harmful (valid SQL that deletes rows).
  • Tokenizer mismatch producing dead ends.
  • Over-large grammars making decoding slow.
  • Left-recursive or ambiguous rules not supported by the engine.

Troubleshooting

  • Generation stalls or ends early — Check the grammar for dead ends and ensure an end-of-sequence path is allowed.
  • Slow decoding — Simplify the grammar; precompile; use engine-recommended features.
  • Valid but unsafe commands — Whitelist operations in the grammar and run in a sandbox with least privilege.

Contrasted with

  • JSON Schema — JSON Schema describes JSON documents only; a grammar can describe any formal language.
