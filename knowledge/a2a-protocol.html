A2A (Agent2Agent) Protocol

protocolfreshness: volatilekey claims checked 2026-10-09

A2A is an open protocol for communication between independent AI agents — discovering each other's capabilities, exchanging tasks and returning results — complementing MCP, which connects agents to tools.

Short answer: A2A lets agents built by different teams or vendors collaborate: they advertise capabilities (an "agent card"), delegate tasks, stream updates and return artifacts. MCP connects an agent to tools; A2A connects agents to agents. Details are version-dependent — verify against the current spec.

What is it?

MCP is how an agent plugs into tools and data. A2A is how one agent talks to another agent — possibly built by a different company on a different framework. They publish what they can do, hand tasks to each other and send back results, so agents can cooperate without sharing internals.

Also known as: A2A, Agent2Agent, agent to agent protocol, agent-to-agent communication, agent card, A2A protocol, Google A2A, interoperable agents.

Technical definition

A2A was announced by Google on 9 April 2025 and contributed to the Linux Foundation, which launched the Agent2Agent project on 23 June 2025; the project released its first stable specification, version 1.0.0, in 2026 (time-sensitive). Core concepts as commonly described: an Agent Card (a JSON description of an agent's identity, endpoint, skills and auth requirements, served at a well-known URL — /.well-known/agent-card.json in the current specification); tasks with lifecycle states; messages made of typed parts; artifacts as outputs; and streaming/push updates for long-running work. The current specification separates an abstract data model and operations from protocol bindings, and defines JSON-RPC 2.0, gRPC and HTTP/REST bindings, with Server-Sent Events for streaming. The specification is evolving, so field names, paths and transports must be checked in the current spec.

When should I use it?

Consider when independently owned agents must interoperate; for in-process orchestration use your framework's native multi-agent features.

Implementation patterns

  • Publish an agent card describing skills and auth for remote agents.
  • Delegate a long-running task and subscribe to status updates.
  • Wrap an existing framework agent behind an A2A server.
  • Gateway pattern: one orchestrator discovers and routes to specialist agents.

Technologies and frameworks

Commonly associated: A2A SDKs (Python, JavaScript and others), JSON-RPC / HTTP, Server-Sent Events, OAuth/OIDC for authentication. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Check whether you need cross-team/vendor interoperability at all.
  2. Read the current spec and pick SDKs.
  3. Define agent skills and publish a card.
  4. Implement authentication and authorisation.
  5. Add timeouts, logging and result validation.

Common failure modes

  • Treating a remote agent's output as trusted input (see What is Prompt Injection?).
  • Weak authentication between agents.
  • Spec/version mismatch between client and server.
  • Over-engineering a single-team system that a function call would solve.
  • Unbounded delegation loops.

Troubleshooting

  • Client cannot find the agent — Check the well-known card path and version in the current spec.
  • Task hangs — Check task state handling, timeouts and streaming support on both sides.
  • Unexpected actions from a remote agent — Treat results as untrusted; restrict permissions and require confirmation.

Contrasted with
