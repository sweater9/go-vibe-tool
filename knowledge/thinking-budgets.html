Thinking Budgets and Reasoning Effort

techniquefreshness: volatilesources not yet verified

Many reasoning models let you cap or tune how much reasoning they do per request. Setting it well balances accuracy, latency and cost.

Short answer: Reasoning effort / thinking-budget settings limit or tune reasoning tokens per request. Start low, measure accuracy on your cases, raise only where it pays, and keep output limits large enough to finish.

What is it?

Reasoning costs tokens. Many reasoning models therefore let you choose how hard they think — for example a low/medium/high setting or a maximum token allowance for thinking. More thinking can help on hard questions but makes answers slower and more expensive.

Also known as: reasoning effort, thinking budget, budget tokens, max reasoning tokens, reasoning effort setting, low medium high reasoning, extended thinking settings.

Technical definition

Providers expose controls such as effort levels or maximum reasoning-token budgets; names, semantics and defaults differ per provider and model and are subject to change. Reasoning tokens usually count toward output limits and billing even when not returned (Reasoning Transparency and Hidden Reasoning). Effective use requires measuring the accuracy-latency-cost frontier on your own tasks (How to Evaluate AI Systems and Outputs).

Entity type: technique · Freshness class: volatile.

When should I use it?

Use whenever you deploy a reasoning model and care about cost or latency.

Implementation patterns

  • Default low, escalate on failure: retry with higher effort only if a check fails.
  • Per-route settings: low for chat, high for code review.
  • Timeouts and streaming for UX.
  • Cost guardrails: max tokens per request and per user.

Technologies and frameworks

Commonly associated: provider API reasoning parameters, usage / token accounting fields. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Find the provider's current parameter names in its docs.
  2. Benchmark each setting on your evaluation set.
  3. Pick the cheapest setting meeting your quality bar.
  4. Set output limits with headroom.
  5. Monitor cost and latency in production (LLM Observability (Tracing, Logging and Monitoring)).

Common failure modes

  • Budget too small, causing weak answers.
  • Output limit smaller than reasoning plus answer, causing truncation.
  • One global setting for very different tasks.
  • Cost surprises because reasoning tokens are not visible.

Troubleshooting

  • Truncated or empty answers — Raise max output tokens; confirm how your provider counts reasoning toward it.
  • Bills higher than expected — Read usage fields for reasoning-token counts; lower effort.
  • Accuracy dips after lowering effort — Raise it only for the task types that regressed.

Contrasted with

  • Test-Time Compute (Inference-Time Scaling) — Test-time compute is the general idea; a thinking budget is one provider control for it.
