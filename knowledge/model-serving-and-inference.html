Model Serving and Inference Infrastructure

conceptfreshness: volatilesources not yet verified

Serving turns a trained model into a reliable service: loading it on suitable hardware, batching requests, managing memory, scaling, and meeting latency and cost targets.

Short answer: Key concerns: latency (time to first token, tokens/second), throughput, memory (weights + KV cache), batching, scaling and cost per request. Use a serving engine suited to your hardware and traffic, and load-test with realistic prompts.

What is it?

Running a model for real users is an engineering problem: it must answer quickly, handle many people at once and not cost a fortune. Serving software and GPU choices decide that.

Also known as: LLM serving, inference server, inference optimization, time to first token, TTFT, tokens per second, throughput vs latency, model deployment.

Technical definition

LLM inference has a compute-bound prefill phase and a memory-bandwidth-bound decode phase. Techniques: continuous batching, paged KV cache (KV Cache), quantisation (Quantization of AI Models), speculative decoding (Speculative Decoding), tensor/pipeline parallelism, prefix caching, request routing and autoscaling. Metrics: TTFT, inter-token latency, tokens/s, GPU utilisation and cost per million tokens. Engines include vLLM, llama.cpp-based servers, TensorRT-LLM, and managed endpoints from cloud and model providers; verify features per version.

Entity type: concept · Freshness class: volatile.

When should I use it?

Relevant to anyone self-hosting models or choosing managed endpoints.

Prerequisites and related concepts

Understand these first: What is a Large Language Model (LLM)?, GPUs and AI Accelerators.

Related concepts: vLLM, KV Cache, Quantization of AI Models, Speculative Decoding, LLM Cost Optimization, LLM Observability (Tracing, Logging and Monitoring), Local and Self-Hosted LLM Runtimes Compared.

Implementation patterns

  • Separate gateway (auth, rate limits, routing) from model servers.
  • Autoscale on queue depth or GPU utilisation.
  • Warm pools to avoid cold-start latency.
  • Canary new model versions.
  • Cache repeated prefixes/responses where safe.

Technologies and frameworks

Commonly associated: vLLM, TensorRT-LLM, Triton Inference Server, KServe, Ray Serve, managed model endpoints. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Collect real prompt/response length distributions.
  2. Estimate memory: weights + KV cache × concurrency.
  3. Choose engine and hardware.
  4. Load-test and set SLOs.
  5. Add monitoring and autoscaling.

Common failure modes

  • Cold starts of large models.
  • OOM from long contexts and high concurrency.
  • Benchmarking with unrealistic prompts.
  • Single point of failure.
  • No back-pressure or timeouts.

Troubleshooting

  • High tail latency — Limit max context/output; tune batching; add replicas.
  • Cost too high — Quantise, route easy requests to smaller models, cache (LLM Cost Optimization).
