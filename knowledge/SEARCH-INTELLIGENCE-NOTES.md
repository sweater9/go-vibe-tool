# Knowledge search intelligence: design notes and QA guide

Branch `feature/knowledge-v4-search-intelligence`, targeting `feature/knowledge-v4-learning` (PR #32). This is a candidate for independent QA. It has not been merged or deployed, and nothing here declares production readiness.

Generated evidence lives beside this file: `SEARCH-INTELLIGENCE-REPORT.md` (before/after on 303 queries), `SEARCH-INTELLIGENCE-HELDOUT.md` (69 queries not used for tuning) and `SEARCH-INTELLIGENCE-BROWSER.md` (browser and size results).

## Architecture

The lexical core `search-core.mjs` is unchanged in behaviour, and the committed index and lexicon are untouched, so "before" stays reproducible. The only edit to the core is a bounded cache around the pure `normalize()` function plus one `export`; it roughly halves latency for both engines.

`search-intelligence.mjs` wraps the core. It is deterministic, runs entirely in the browser and has no model or external call.

| Step | What it does |
| --- | --- |
| Understand | Detects intent (definition, how-to, comparison, troubleshooting, sequence), level (beginner or advanced) and strips framing such as "how do I". |
| Repair | Expands curated abbreviations (ml, vlm, moe...), fixes single-word typos by edit distance (unique best match only) and splits run-together words. Every rewrite is reported to the visitor ("Showing results for ..."). |
| Rank | Rescoring uses IDF-weighted coverage of a guide's *name* (title, question, aliases, id) after light, symmetric stemming. Keywords and summaries never create an anchor. Comparison pages are demoted unless a comparison was asked for. |
| Decide | The core's confident answer stands unless a narrow-anchor gate vetoes it (one shared word plus unexplained words) or another guide beats it by 3+ points. A shared keyword alone never becomes a confident answer. |
| Shape | Broad subjects with no single guide return a topic cluster (`hubs`). Ambiguous bare words return options, not a guess. |
| Recommend tools | `tool-map.json` (below). |
| Related guides | Typed links from `relations.json`: prerequisite, next step, compare, practical, related. |

Curated data (all validated by tests): `query-understanding.json` (abbreviations, hubs, ambiguous words, intent phrases with context guards), `tool-map.json`, `relations.json` (generated by `node knowledge/src/build-relations.mjs` from the ontology, `index.related` and the learning paths; prerequisites are acyclic and `--check` fails if the file is stale).

### Semantic search
Still opt-in (`?semantic=1`) and unchanged in policy. When enabled, the hybrid engine is injected as the *engine* underneath the intelligence layer. If semantic assets fail to load, `search.js` drops to lexical; if the intelligence layer throws, it falls back to the base engine; if any of the three JSON files is missing, the rest still works. Each case is covered by tests.

A tool appears alongside a Knowledge answer and never replaces it; when no guide is confident (for example "compress a png image") the tool is still offered.

## For Agent 1 (learning paths)

- `knowledge/relations.mjs` is a pure API (`createRelations(json)`: `prerequisites`, `nextSteps`, `comparisons`, `practical`, `related`, `learningOrder`). It has no DOM, tolerates unknown ids and missing data, and does not touch `learning-paths.mjs` or the learning panel.
- `search.js` hunks (all additive; the V4 panel code is untouched): `appendTools()` helper, `loadIntelligence()` and its call in `load()`, the engine selection and rewrite note at the top of `render()`, the disambiguation and tool block in the weak branch, the cluster block, the relation label in learn-more. If you also edit `render()`, expect a textual conflict in those spots only.
- `package.json` and `.github/workflows/quality.yml` gained script and branch entries; the workflow now also triggers on `feature/knowledge-v4-learning`.

```
npm install --no-save playwright@1.56.0 && npx playwright install chromium firefox webkit

```
By hand at `/knowledge/`: try "Machine learning", "transfomer attention", "how do I remove personal data from text before sending it to an AI", "compress a png image", "graph", "rag vs fine tuning", "what to learn after rag", "best pizza in new york". Block `relations.json` or `search-intelligence.mjs` in devtools and confirm plain search still answers. Try `?semantic=1` with `semantic-index.json` blocked.

## Known limitations

- Conversational paraphrases with no shared vocabulary ("a small model learning from a bigger one") are still not confident. That is the deterministic ceiling; the opt-in semantic path is the intended help and was not used for the reported numbers.
- The 303-query dataset was used to tune the layer, so its 100% is an upper bound. The held-out set (written afterwards, not tuned on) is the better estimate; see its file. One held-out item ("model") exposed a real bug class and was fixed by adding the word to `ambiguous`; the held-out file notes the first-run numbers.
- Same author wrote both sets, so neither is fully independent. QA should add its own queries.
- `relations.json` only knows guides present in the ontology or index; the 117 guides without an ontology entry get `related`/`next` links from `index.related` and learning paths only.
- Bare `token` still answers LLM tokens (existing behaviour kept); other overloaded words offer a choice.
- Firefox and WebKit could not be downloaded in the authoring sandbox (blocked network), so only Chromium ran locally. CI installs all three; QA should run the browser test on them.
- Added payload is 144 KB / 28 KB (raw/gzip) on top of a 447 KB index. The layer loads asynchronously after first paint and lexical search works before it arrives.
