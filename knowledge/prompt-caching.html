Prompt Caching

techniquefreshness: volatilesources not yet verified

Prompt caching lets a provider or serving engine reuse the computation for a repeated prompt prefix — such as a long system prompt or document — cutting latency and often cost on later requests.

Short answer: Put stable content first (instructions, tools, documents) and variable content last, so repeated prefixes hit the cache. Rules (minimum length, expiry, pricing, how to mark cacheable content) are provider-specific and change — check current documentation.

What is it?

If every request starts with the same long instructions or document, there's no need to process them from scratch each time. Prompt caching remembers the work for that repeated beginning, so follow-up requests are faster and, with many providers, cheaper.

Also known as: context caching, prefix caching, cache prompts, cached tokens, reduce LLM cost caching, cache_control, KV cache reuse, prompt cache hit.

Technical definition

Implementation reuses the KV Cache for identical token prefixes (self-hosted engines offer automatic prefix caching). Hosted APIs expose varying mechanisms: automatic or explicit cache markers, minimum prefix lengths, time-to-live windows and distinct pricing for cache writes and reads. Any change early in the prefix invalidates later cache hits. Cache effects on determinism, data retention and privacy should be reviewed in provider terms.

Entity type: technique · Freshness class: volatile.

When should I use it?

Valuable with long, repeated prefixes (RAG documents, agent tool lists, few-shot examples).

Prerequisites and related concepts

Understand these first: What is a Context Window?, KV Cache.

Related concepts: LLM Cost Optimization, Context Engineering, What is a System Prompt?, Model Serving and Inference Infrastructure, vLLM.

Implementation patterns

  • Order prompt: static instructions → tools → documents → dynamic user content.
  • Keep prefix byte-identical (no timestamps/IDs early).
  • Warm caches for high-traffic prompts.
  • Measure hit rate.

Technologies and frameworks

Commonly associated: provider caching features, vLLM automatic prefix caching. Names are examples of what exists, not recommendations, and projects change quickly.

Practical guide

  1. Read the provider docs.
  2. Reorder the prompt.
  3. Log cached-token counts.
  4. Tune for your traffic pattern.

Common failure modes

  • Dynamic data at the start breaking prefix matches.
  • Prefix below minimum length.
  • Cache expiry between sparse requests.
  • Assuming cached = free.

Troubleshooting

  • Low hit rate — Move variable text later; keep prefix identical; check minimum length and TTL.
  • Costs unexpectedly high — Compare cache-write and read pricing to your request frequency.

Contrasted with

  • KV Cache — The KV cache is the data structure; prompt caching is the feature of reusing it across requests.
